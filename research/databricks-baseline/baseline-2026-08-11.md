# Databricks platform baseline

**Baseline 2026-08-11 · Rev 2**

The platform model the review-prep tier reasons against. Three sections survived review: product
surfaces, the object model, and personas. Everything else was cut — see the revision log.

Derived from the `db-bricksearch` plugin. Sources and dates are in [`README.md`](README.md).
What is still missing, and the questions that would fill it, are in
[`open-questions.md`](open-questions.md).

## Product surfaces

**Incomplete, and known to be.** These six are the chapter headings of one reference file, not the
product. Question 1 in `open-questions.md` asks for the real list, read off the navigation.

**Governance and Unity Catalog.** UC metastore, catalogs, schemas, tables, volumes; privileges;
column-level lineage; tags; data classification; row and column filters; Delta Sharing; Lakehouse
Federation; AI governance; security and compliance including ABAC, audit logs, SSO and SCIM,
encryption and secrets; the admin console; cost governance; performance governance including
Lakehouse Monitoring, query profile and liquid clustering. Read by platform admins, governance
admins, metastore admins, stewards, security and audit.

**AI/BI.** Dashboards — datasets, visualizations, filters, publishing, scheduling, embedding.
**Genie** for natural-language query over UC data, with spaces and a curated Knowledge Store.
**Genie Code**, which generates whole dashboards from a prompt. **Databricks One** as the
business-user portal. **Metric Views** as the semantic layer. The SQL editor and SQL warehouses.

**Compute and serverless.** Classic clusters, serverless, three SQL warehouse tiers, Photon, jobs
compute, instance pools, cluster policies. Policy enforcement exists for classic clusters and has no
serverless equivalent.

**GenAI and MLOps.** Foundation Model APIs, Model Serving, external models, Vector Search, AI
Playground, Agent Framework, **Agent Bricks**, **AI Gateway** for safety filtering, guardrails, rate
limiting and inference logging, **MLflow**, Feature Store, agent evaluation and monitoring. Mosaic AI
is the umbrella brand.

**Pipelines and data engineering.** **Lakeflow Connect** for managed ingestion, **Lakeflow
Declarative Pipelines**, **Lakeflow Jobs** for orchestration, Auto Loader, Structured Streaming,
Delta Lake with liquid clustering. Lakeflow is an umbrella over three distinct products and
collapsing them is a naming error.

**New and emerging.** **Lakebase**, serverless managed Postgres with OLTP-to-Delta sync tables,
branching, pgvector and UC governance. **Lakewatch**, an agentic SIEM on Delta Lake. **Databricks
Apps**, running Streamlit, Gradio, Dash and Flask on serverless under UC. **Marketplace**, which
distributes data, models, notebooks and MCP servers. **Partner Connect**.

**No reference file covers notebooks or the workspace shell** — arguably the most central surface in
the product. A tag exists for it and nothing else.

## Object model

**No source states the hierarchy.** The chain below is reconstructed; the details under it are cited.
Three gaps are called out at the end and are the subject of blocks 2 to 4 in `open-questions.md`.

```
Account ─┬─ Metastore ── Catalog ── Schema ── { Table · View · Volume · Model ·
         │                                      Function · Metric View }
         └─ Workspace ── { Notebook · Job · Pipeline · Query · Dashboard ·
                           Genie space · Experiment · Endpoint · Cluster ·
                           Warehouse · App }
```

The **account, workspace and metastore split is load-bearing** rather than incidental. It is the axis
the permission model turns on, and roles are scoped inconsistently across it — one is account-scoped
where a neighbouring one is metastore-scoped, which is an open design problem rather than a settled
design.

- **Privileges:** `BROWSE · USE · SELECT · MODIFY · MANAGE · APPLY TAG`
- **Admin roles, five:** Account, Workspace, Metastore, Billing, Marketplace
- **Tag types, three:** Custom (user-defined), Governed (policy-enforced), System (predefined and
  immutable)
- **Tag inheritance is narrower than people assume.** Catalog to schema to table inheritance applies
  **to policy evaluation only** — not to metadata display and not to columns. Column tags are set
  explicitly, and there is **no propagation along lineage**
- **Notebooks are UC objects**, and carry tags including system tags for certification and
  deprecation

### The three gaps

**Control plane and data plane.** Absent entirely. This decides what a surface can promise: which
operations need a running data plane resource, what is slow or unavailable because of where the data
lives, and what may not leave the customer's account. Serverless does not fit the classic two-way
split, which makes it more important to have written down rather than less.

**Compute.** The surfaces section names the compute types; there is no object model behind them. No
lifecycle state machine for a cluster or a warehouse, no list of what a user configures versus what is
automatic, no failure modes. A workbench that cannot say what states a cluster passes through cannot
design the waiting.

**AI and ML.** Named as brands rather than modelled as objects. Experiment, run, model version,
alias, trace, endpoint, served entity, vector index, feature table, agent, tool — the relationships
between these and how much of it Unity Catalog governs are unknown here.

## Personas

The one section that came back well covered, and the caveat is still worth keeping: it comes from a
single research output and it is **governance-specific**. There is no documented data engineer,
analyst or data scientist persona anywhere in the source material.

The source PRD is explicit that these "do not necessarily equate to specific job titles but rather
roles and responsibilities."

| Persona | Cares about | Access reality |
|---|---|---|
| **Data steward** | Business context, metadata quality, classification, certification | **Locked out** — not an admin |
| **Data / governance admin** | Policy, access control, compliance posture | Has access |
| **Platform engineer** | Reliability, config, workspace and metastore setup | Partial |
| **FinOps / billing admin** | Spend, forecast, chargeback | Wanted a cost-viewer role |
| **Security / auditor** | Access posture, sensitive-data exposure, audit trail | Wanted a cross-domain reader role |
| **Executive** | Portfolio-level governance health | Locked out |
| **Catalog / domain owner** | Their own slice of the catalog | Locked out |
| **Business user** | Answers from data, no workspace navigation | Databricks One is built for them |

The pattern worth carrying into a critique: **the beneficiaries are precisely the non-admins.** A
governance surface that introduces no new permissions is gated to the five admin roles, and the
majority of Private Preview customers asked for it to be opened up. One customer put it plainly: "no
one in the call is an account, workspace, or metastore admin — if GovHub is only account admins then
Houston we have a problem."

The set maps onto the DMBOK/DAMA governance operating model, which is the argument that it is stable
rather than invented.

One trap: the source's "business function" tags — `#pmm`, `#uxr`, `#design`, `#field-eng` and the
rest — are **internal Databricks org functions describing who produced a research artifact.** They
are not end-user personas and they read like they might be.

## What this does not cover

Named plainly so review prep knows when to stay quiet. Everything here is a block in
[`open-questions.md`](open-questions.md).

| Missing | Consequence for review prep |
|---|---|
| A complete surface list | Cannot reliably say "this overlaps X" — the map has holes |
| Control plane and data plane | Cannot reason about latency, availability or data residency |
| Compute object model | Cannot critique waiting, failure or configuration |
| AI and ML object model | Cannot critique the fastest-moving part of the product |
| External positioning per area | Cannot argue from the customer's side |
| Customer voice per area | Cannot say "your users already tell you this" |
| Legal and regulatory | Cannot flag the compliance bottleneck, which is often the real blocker |
| Notebooks, workspace shell, developer experience | No backing at all. Ask, never assert |
| Non-governance personas | No documented engineer, analyst or scientist |
