# Token simplification

Proposal. Nothing here is implemented. Every number is generated by
`scripts/measure-dimensional-usage.mjs` and every claim about Tailwind is asserted by
`scripts/verify-spacing-scale.mjs`, which passes 59 of 59.

## The principle

DBUI defines every dimensional value. Tailwind's open-ended multipliers are switched off so only
DBUI steps exist. A step we did not define does not render the wrong value, it renders no class at
all.

| Requirement | How it is met |
|---|---|
| Full definition | Every utility resolves to a `--db-*` custom property |
| Portability | `--db-*` are plain custom properties, readable by StyleX, plain CSS or Figma. Moving off Tailwind is a re-bridge, not a re-definition |
| Constraint | `--spacing: initial` removes the multiplier. 8, 12, 16 and 24 compile. 6, 10, 14 and 28 do not |
| Density | Each step is `calc(unit * N * density)`, resolved by the browser. At 1.2 a 12px padding renders 14.4px |

Three layers, in order. The middle one is the only Tailwind-specific thing in the system.

```
--db-space-3: calc(var(--db-spacing-unit) * 3 * var(--db-density-scalar))   definition
--spacing-3: var(--db-space-3)                                              bridge
p-3                                                                         authoring
```

## Read this first

**This proposal does not reduce the token count.** It converts tokens from decorative to
load-bearing. 202 properties ship today and 199 ship after. Families go from 9 to 11.

The change worth having is not fewer tokens. It is that today a designer can write `p-2.5` and get
10px, and no token in the system objects. After this, `p-2.5` is not a class.

## What the compiler actually does

Asked directly, not read from documentation. `scripts/verify-spacing-scale.mjs` compiles fixtures
against the installed Tailwind 4.2.2 and asserts the output.

| Claim | Observed |
|---|---|
| `--spacing: initial` disables the multiplier | Yes. `p-5`, `p-2.5`, `p-7`, `p-9`, `gap-13` and `mt-10` all emit nothing |
| A defined step still emits | Yes. `p-3` emits `padding: var(--db-space-3)` |
| The value is ours, not a copy | Yes. The utility carries the `--db-*` reference, not a resolved length |
| Density survives | Yes. Nothing is flattened at build time, so the browser resolves `calc(unit * 3 * density)` per render |
| Half steps work | Yes. `--spacing-0\.5` is a valid key and can point at `--db-space-0-5`, so no backslash enters the portable name |
| Bracket values still compile | Yes. `p-[13px]` emits `padding: 13px`. The compiler cannot close this, only the linter can |
| Keyword utilities are untouched | Yes. `h-full`, `w-px`, `inset-0`, `h-auto` and `max-w-none` are unaffected |

Nineteen utility families read the spacing key: padding, margin, gap, inset, top, right, bottom,
left, translate, width, height, min and max of both, scroll margin, scroll padding, indent and
basis. Constraining the key constrains all nineteen at once.

## The shared-scale problem

One key cannot serve padding and control height and layout width, because they disagree.

| Axis | Wants | Conflict |
|---|---|---|
| Padding and gap | 8, 12, 16, 24 | — |
| Control height | 24, 28, 32 | 28 is a 7-step, explicitly rejected for padding |
| Layout width | 240px rail, 280px panel | Not a multiple anyone wants in a padding scale |

Measured on a constrained spacing scale, `h-7` dies although 28px is an approved control height,
and `w-60`, `w-70`, `max-w-176` and `min-w-56` all die with it.

### Resolution

Tailwind v4 has separate namespaces for these, which removes the conflict entirely. This was not
obvious and is not in `theme.css`, so it was tested.

| Namespace | Drives | Verified |
|---|---|---|
| `--spacing-*` | padding, margin, gap, inset, translate, scroll, basis, indent | yes |
| `--height-*` | `h-*`, `min-h-*`, `max-h-*` — all three from one key | yes |
| `--width-*` | `w-*` only | yes |
| `--min-width-*`, `--max-width-*` | `min-w-*`, `max-w-*` — width is asymmetric with height here | yes |
| `--size-*` | `size-*`, falling through to `--spacing-*` when undeclared | yes |

Two behaviors make this cheap:

- Where both define the same step, `--height-*` wins. Tested with `--height-6` against
  `--spacing-6`. So 28px can be legal as a height and illegal as a padding at the same time.
- An undeclared height step falls through to the spacing scale. `--height-*` only needs the steps
  spacing refuses, so it is five declarations, not fifteen. `size-4` on 81 icon call sites keeps
  working with no `--size-4` declared at all.

**Recommended: separate namespaces, numeric steps in each.** Rejected alternatives:

| Option | Why not |
|---|---|
| One generous scale, linter constrains | Requirement 3 becomes advisory. The compiler already enforces for free |
| Tight spacing, widths left to brackets | Widths stay ungoverned, which is the state we are trying to leave |
| Named steps (`p-space-md`) | Longer to write, and the numeric name matches how the values are already thought about |

## The proposed scale

Step N is N times the 4px unit, which is how the config already computes and how the class already
reads.

| Scale | Steps | Resolved |
|---|---|---|
| `--db-space-*` | 0, 0.5, 1, 2, 3, 4, 6, 8, 12 | 0, 2, 4, 8, 12, 16, 24, 32, 48px |
| `--db-height-*` | 5, 7, 10, 12, 14 | 20, 28, 40, 48, 56px |
| `--db-size-*` | 3.5, 5, 10 | 14, 20, 40px |
| `--db-width-*` | rail, panel | 240, 280px |

Height and size list only what spacing refuses. Everything else arrives by fall-through.

Width is named rather than numeric because 240px is not a multiple of anything meaningful, and
because the twelve bracket widths in the repo today are the evidence that a numeric scale was never
going to hold them.

**The 6px and 10px steps are the finding.** They are the two values called out as illegal, and

Deciding the scale is therefore also deciding that menu padding moves from 6px to 8px. That is a
visible change to the densest surfaces in the product and it should be looked at in Figma before
the scale is agreed, not after.

## Border, and the contradiction

The brief asks to rename border to `none / base / strong` and to delete border width as superseded.
Both cannot happen. Two readings.

| Reading | Family | Live today | Fits `none`? |
|---|---|---|---|
| A — border **width** | `--db-border-width-{none,thin,thick}` | 0 consumers. 98 width utilities all render Tailwind's baked values | Yes. `none` is a width |
| B — border **color** | `--db-border-{base,strong,subtle,inverse,disabled,accent}` | 104 uses counting the three `--db-input-border-*` siblings. `border-base` 30, `border-disabled` 13, `border-strong` 9 | No. There is no "no color" |

**Recommended: reading A, border width.** `none` gives it away, and it is the family with exactly
three members.

But **delete is the wrong verb under the new principle.** The family is unread precisely because it
was never bridged. Tested:

- `--default-border-width` moves a bare `border`. The hairline on 47 call sites is ownable in one
  line.
- `--border-width-*` is a real namespace and mints named width classes.

So border width should be kept and bridged, which is the opposite of deleting it.

**One objection to the names, stated once.** `--border-width-strong` mints the class `border-strong`,
which would sit one token away from `border-border-strong`, a live color on 9 sites. Two classes,
nearly the same name, different properties. Recommend keeping `none / thin / thick` and bridging
only `--default-border-width`, which gives ownership of the hairline without minting a colliding
class. Presented as decided either way.

Separately: `border-subtle`, `border-inverse` and `border-accent` have zero uses in system code.
Flagged, not proposed.

| Class | Uses | After |
|---|---|---|
| `shadow-none` | 35 | Unchanged, a keyword |
| `shadow-xs` | 31 | **Rewrite to `shadow-sm`.** Pixel-identical, but it is a code change on 18 files |
| `shadow-md` | 15 | Unchanged, identical value |

Two things are not no-ops and should be agreed as changes, not as renames: the dark values, which
take dark-mode menus and dialogs from nearly flat to visibly lifted, and the one `tabs.tsx` site.

## Motion

Decided: `slow 450 / default 300 / fast 150`, replacing six band members that nothing reads.

Bridging is asymmetric, and this was tested:

| Key | Is it a namespace? | Consequence |
|---|---|---|
| `--duration-*` | **No** | `duration-slow` emits nothing. Named durations need `@utility` |
| `--default-transition-duration` | Yes, overridable | One line moves every un-pinned transition |
| `--ease-*` | Yes | `--ease-standard` mints `ease-standard`, so our easing finally becomes reachable |

### The override is a separate decision

31 transition call sites exist. Exactly one pins a duration. The other 30 run at Tailwind's 150ms
default. Setting `--default-transition-duration` to `default` moves all 30 to 300ms.

The 14 `duration-100` uses are not affected. Thirteen sit beside `animate-in` or `animate-out`,
which are CSS animations rather than transitions.

**Recommend setting it to `fast`, not `default`.** 150ms is what those 30 sites already run at, so
the override becomes a literal no-op that transfers ownership without changing feel. 14 of the 30
are `transition-colors` on hover, and 300ms on a hover reads as lag. Reserve `default` and `slow`
for entrances and panels, reached through an `@utility` rather than the global default.

Presented as decided at 300ms if that is the call. The 30 sites are the blast radius either way.

## Radius, reconsidered

**Yes, radius is already the model.** `--db-radius-*` bridges to `--radius-*`, 156 call sites read
it and the verification confirms the override works. It is the shape space and size should copy.

It is not finished, though. Three gaps:

| Gap | Detail |
|---|---|
| `--radius-xs` and `--radius-4xl` never overridden | `rounded-xs` and `rounded-4xl` compile and render Tailwind's values. Close both with `initial`, verified to work without disturbing the six that are ours |
| `rounded-full` is not ours | 32 call sites render Tailwind's baked `calc(infinity * 1px)`. `--db-radius-full` is reachable only through `rounded-3xl`, which nothing writes, so it is effectively dead. `--radius-full` is overridable — tested. Bind it and drop the `3xl` mapping |
| Six bracket radii | `rounded-[2px]` on 3 sites plus `[1px]`, `[4px]`, `[8px]` and two `calc()` forms. 2px is `--radius-xs`, which the same change closes |

## The control-height lint rule

| Aspect | Specification |
|---|---|
| Where | `checkClassName` in `scripts/design-lint/react-lint.js`, which already receives the tag name as `element` |
| Inspects | `h-*`, `min-h-*` and `size-*` on a JSX element whose tag is in an interactive allowlist |
| Approved | 24px `h-6`, 28px `h-7`, 32px `h-8` plus the `size-` equivalents for square controls |
| Ignores | `h-auto`, `h-full`, `h-fit`, `h-screen`, `h-px` and CSS-variable heights. These are layout, not a control size |
| Ignores | `max-h-*`, which is a ceiling |
| Ignores | Any class inside an `[&_svg]` or `[&>svg]` variant, which sizes an icon |
| Level | `warning`, matching the other advisory spacing rules |
| Escape | A line comment, consistent with how the other rules are suppressed |

The allowlist matters more than the rule. It must be controls, not every component. A height on
`<Card>` is layout and the rule must not fire.

### The components themselves are a different question

The linter never reads CVA variant tables in `.ts`, so the rule would not police them. Scanned
anyway, because agreeing to 24/28/32 means agreeing that these are exceptions. Of 29 `h-*` and
`min-h-*` utilities across 14 control files, 19 are on the set and 10 are not.

| Height | Sites | Components |
|---|---|---|
| 8px | 1 | table |
| 12px | 1 | switch |
| 16px | 1 | switch |
| 20px | 4 | segment-control, dropdown-menu, context-menu, menubar |
| 40px | 1 | table |
| 56px | 1 | textarea |
| arbitrary | 1 | combobox |

20px on menu shortcuts and the segment control is the one worth a decision. The rest are genuine
exceptions: a switch track is not a control height, a textarea minimum is not a control height and
a table header at 40px is a deliberate choice.

Square controls are counted separately and deliberately. `size-*` is not a control-height signal —
81 of its 141 uses are `size-4` on an icon, usually written bare on the icon element with no variant
to mark it. Folding the two together reported 16px as the most common control height in the system,
which is false. It is the most common icon size.

## What actually shipped

The proposal above is kept as written, because it is the argument. This section is the outcome, and
where the two disagree the outcome is what is in the code.

Four semantic families ship, not the seven the proposal sketched. `height`, `width` and the split
`size` families collapsed into one `size`, because Tailwind reads `h-*`, `w-*` and `size-*` from
three separate keys that one family can populate — the namespaces are Tailwind's, the family is
ours. Named widths were not adopted; the bracket widths remain.

| Family | Stops | Resolved |
|---|---|---|
| `--db-space-*` | 0, 0.5, 1, 2, 3, 4, 6, 8, 10 | 0, 2, 4, 8, 12, 16, 24, 32, 40px |
| `--db-size-*` | 2, 3, 4, 5, 6, 7, 8, 10, 12 | 8, 12, 16, 20, 24, 28, 32, 40, 48px |
| `--db-radius-*` | 0, 1, 2, 3, 4, 6, `full` | 0, 4, 8, 12, 16, 24px, pill |
| `--db-border-*` | 0, 1, 2 | 0, 1, 2px — literal, never scaled |

Differences from the proposed scale worth naming:

- **Space gained 10 (40px) and lost 12 (48px).** 48px had no call site the 40px stop could not
  serve, and ending the ladder at 10 keeps every stop a multiple the eye can count.
- **Space kept 0.5 (2px).** It is the inset-track pattern on 42 sites — `p-0.5` on the toggle group,
  `py-0.5` on badges — where a control sits in a groove one hairline wider than itself. It is the
  only half step, and it is not a precedent.
- **Space dropped 5 (20px), 7 (28px) and 12 (48px)** after they were briefly included. Their call
  sites are handled by the snap pass below.
- **Size kept 6 (24px)** against an earlier decision to drop it. 24px is the small control height —
  `h-6` on the small button — and a size scale that cannot express the system's own button is not a
  size scale.
- **Size later gained 5 (20px) and 12 (48px)**, which takes it to nine stops. 20px is the chip
  height on badge, tag, kbd, all three menu shortcut slots, the small segment control and the
  avatar. 48px is the platform header, already codified in `src/rules/layout-rules.ts` as the
  shell's `headerHeight`. Both rendered correctly off the multiplier the whole time, which is why
  neither was missed — the pixels were right and the decision was not written down.
  So 6 is a stop in both families while 5, 7 and 12 are stops in only one: `h-5` is `--db-size-5`
  and `p-5` is still the multiplier.
- **Size does not carry 14 (56px).** The one 56px was the textarea's `min-h`, a floor that grows
  with content rather than a height the system sets, and it was moved to `min-h-12`.
- **`radius-full` is bridged.** It shipped as a token from the start and never got an `@theme` key,
  so every `rounded-full` rendered Tailwind's `calc(infinity * 1px)` and `--db-radius-full` was
  defined and dead. Both clip identically on anything smaller than 999px, which is why the gap
  survived a whole radius rename. The reason to close it is Figma, which cannot express an infinity
  and so could never state the same pill.
- **Elevation is untouched.** Not renamed, not revalued, no dark variants. The measured problems are
  real and the change was declined as out of scope.
- **The primitive scale does not ship.** Figma holds it as a `scale` collection that designers alias
  into; React gets the four semantics only. There is no `--db-scale-*` in the generated CSS, which
  mirrors how colour primitives already work. Asserted by L1 in `verify-spacing-scale.mjs`.
- **The collection is called Dimensions.** "Scalar" now means a multiplier and nothing else.

## The follow-up pass: snapping call sites

**Nothing in this section is done.** It is the agreed plan for a separate, later change, recorded
here so the rules survive the conversation that produced them.

The scale above is narrower than the values components currently use. Tailwind's `--spacing`
multiplier is deliberately left **on**, so a class like `p-5` still compiles to 20px off the
multiplier rather than failing. Every off-scale call site therefore keeps rendering exactly what it
renders today. That is what makes this change a no-op, and it is also what makes the snap pass
necessary — until it runs, the scale is a recommendation rather than a constraint.

Closing the multiplier (`--spacing: initial`) is the end state and is not part of this pass either.
It only becomes safe once the values below are gone.

### The rules

These are spacing rules and only spacing rules. 20px, 28px and 48px are all legal heights on the
size family, so `h-5`, `h-7` and `h-12` are already on a token and must not be snapped. The pass
moves `p-`, `m-`, `gap-` and their siblings.

| Current | Snaps to | Why |
|---|---|---|
| 6px | 8px | Menu and list-item padding. The densest surfaces in the product, and the largest single group |
| 10px | 12px | |
| 20px | 24px | With one exception, below |
| 20px, Genie list indent | 16px | Down, not up. The indent reads as a nested-list marker, and 24px pushes it into looking like a second level of nesting |
| 28px | — | No rule of its own |

28px needs no rule because it is not an authored value. It is the menu text inset, computed as
6 + 16 + 6 — padding, icon, gap. Apply the 6px rule to its two ends and it becomes 8 + 16 + 8 = 32px
on its own. Writing a separate 28 → 32 rule would be describing the same decision twice.

Each rule moves a value up to the nearest legal stop except the Genie indent, which moves down. Up
is the default because shrinking padding is the change a person notices.

### What to expect

These are real visual changes, unlike everything in this round. Menus get 2px more padding on each
side, which is the one to look at closely because it compounds across a list. The fingerprint
harness will report a large diff and should — the point of that pass is that things move.
