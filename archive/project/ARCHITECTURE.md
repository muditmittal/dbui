# DBUI System Architecture

> Maintainer-only reference. This file lives in `project/` and is gitignored
> so it never ships to consumer projects. The canonical structure for what
> _does_ ship is the `packages/` tree.

The DBUI system is organized in **four layers**. Edit Layer 1, regenerate
Layer 2, expose via Layer 3, automate via Layer 4. Drift is detectable
because everything below Layer 1 is derivable.

## The four layers

```
┌─────────────────────────────────────────────────────────────────┐
│  L1 — SOURCE OF TRUTH        Hand-edited. Canonical.            │
│       (designers/engineers)                                     │
├─────────────────────────────────────────────────────────────────┤
│  L2 — LOOKUPS (registry)     Auto-generated from L1. Never      │
│       (queried by tools)     hand-edited. Drift = build fails.  │
├─────────────────────────────────────────────────────────────────┤
│  L3 — TOOLS (MCP)            Thin wrappers over L2.             │
│       (called by LLMs)       Stable surface, internals iterate. │
├─────────────────────────────────────────────────────────────────┤
│  L4 — PROCESSES              Scripts, rules, skills.            │
│       (when things run)      Trigger tools at the right moments │
│                              in a project's lifecycle.          │
└─────────────────────────────────────────────────────────────────┘
```

**The hygiene rule:** edit L1, everything below regenerates. **Never hand-edit L2.**

│           └── ... (~450 files)

### `packages/dbui-shells/` — compositions + shells

```
packages/dbui-shells/
└── src/
    ├── components/                     internal building blocks
    │   ├── PlatformHeader.tsx

    │   └── AssistantPanel.tsx
    ├── compositions/                   ★ compositions (NEW)

```

### Convention: structured JSDoc tags

Every component, composition, and shell uses tags that L2 extraction reads:

```tsx
/**
 * @category overlay
 * @useFor Detail panels, settings, secondary content
 * @avoidFor Primary workflows → use Dialog
 * @synonyms slide-out, side panel, sheet
 * @figma DBUI Components → Drawer
 * @composition true            // marks this as a composition vs. component
 * @requiresShell BaseShell      // when applicable
 */
export function Drawer({ ... }) { ... }
```

Tags are the lingua franca between the canonical source and L2.

## L2 — Lookups (auto-generated)

Lives at `packages/dbui-mcp/src/data/`. **Never hand-edit.** Regenerated by
`build-data.js` whenever L1 changes.

```
packages/dbui-mcp/src/data/
├── tokens.json                         ← from globals.css
├── components.json                     ← from dbui/src/components/ui/*.tsx
├── icons.json                          ← from dbui/src/components/icons/*
├── compositions.json                   ← from dbui-shells/src/compositions/*.tsx
├── shells.json                         ← from dbui-shells/src/shells/*.tsx
├── component-schemas.json              ← ts-morph: variants, props, slots
├── figma-mapping.json                  ← from Figma + cross-checked w/ React
├── brandvoice-rules.json               ← from dbui/docs/brandvoice.md
└── _manifest.json                      ← hashes for drift-check
```

**Status today:** modular extractor pipeline is live (Apr 28, 2026). All 9 L2 files
are generated by independent extractors at `packages/dbui-mcp/scripts/extractors/*.js`.
Stubs are in place for `compositions.json`, `component-schemas.json`,
`brandvoice-rules.json`, `figma-mapping.json` until their L1 counterparts stabilize
and the extraction logic gets fully wired in.

### The regen pipeline (L1 → L2)

Each extractor in `packages/dbui-mcp/scripts/extractors/` declares:

```js
export const id = "tokens"                                    // unique extractor name
export const inputs = [{ path: "...", kind: "file"|"glob" }]  // L1 sources
export const outputs = ["tokens.json", "hex-tokens.json"]     // L2 files produced
export async function extract() { ... }                        // reads inputs, writes outputs
```

The orchestrator at `scripts/regen-l2.js` hashes every input file (sha256 of contents)
and compares to `scripts/_manifest.json`. Only extractors whose inputs changed run.
**Surgical regen — change one icon, only `icons.json` regenerates. Change a token,
only `tokens.json` + `hex-tokens.json` regenerate.**

```bash
# From packages/dbui-mcp/, or via yarn workspace from repo root:
yarn build:data         # alias for regen-l2 --all (full regen)
yarn regen:l2           # surgical (only changed inputs)
yarn regen:l2:check     # dry-run, list what would regen
yarn regen:l2:list      # list all registered extractors
```

**Renames** (e.g. `Button → PrimaryButton`) are out of scope for surgical regen —
they affect references in `compositions.json`, `figma-mapping.json`, etc. Run
`yarn regen:l2:all` once after any rename to fully resync.

**Manifest** at `packages/dbui-mcp/scripts/_manifest.json` tracks per-extractor
input + output hashes. Never hand-edit; the orchestrator manages it.

## L3 — Tools (MCP)

Lives at `packages/dbui-mcp/src/tools/`. Thin wrappers over L2 data.

```
packages/dbui-mcp/
├── src/
│   ├── index.js                        MCP server entry
│   ├── spec.js                         ★ Spec type (the contract)
│   └── tools/
│       ├── build-structure.js          Stage 1: description → Structure
│       ├── hydrate.js                  Stage 2: Structure + content → Spec
│       ├── validate.js                 Stage 3: Spec → pass/fail
│       ├── render-figma.js             Stage 4: Spec → use_figma JS (real instances)
│       ├── render-react.js             Stage 4: Spec → TSX / Storybook story
│       ├── check-figma-node.js         Post-render: instance-vs-shape ratio
│       ├── lookup-component.js         primitive
│       ├── lookup-icon.js              primitive
│       ├── lookup-token.js             primitive
│       ├── explain-component.js        primitive — variants/slots/example
│       └── (check-copy, check-composition, get-rules, lint-react-snippet)
└── scripts/
    ├── regen-l2.js                     L1 → L2 orchestrator (modular, surgical)
    ├── extractors/                     one extractor per L2 file
    │   ├── _base.js                    shared: hashing, manifest I/O, glob
    │   ├── tokens.js                   globals.css → tokens.json, hex-tokens.json
    │   ├── icons.js                    icon-index → icons.json
    │   ├── components.js               component-index → components.json
    │   ├── rules.js                    composition-rules.ts → rules.json
    │   ├── dbui-components-allowlist.js  → dbui-components.json
    │   ├── compositions.js             compositions/*.tsx → compositions.json
    │   ├── shells.js                   shells/*.tsx → shells.json
    │   ├── component-schemas.js        ts-morph → component-schemas.json (stub)
    │   ├── brandvoice-rules.js         brandvoice.md → brandvoice-rules.json (stub)
    │   └── figma-mapping.js            Figma API → figma-mapping.json (stub)
    ├── _manifest.json                  per-extractor input + output hashes
    ├── build-data.js                   legacy (kept until trust in regen-l2 is high)
    ├── cli.js                          direct-invoke for any tool
    └── (smoke-test.js, loop-smoke.mjs, etc.)
```

**The 3-stage build loop** the LLM follows:

```
Screenshot/prompt
        │
        ▼
1. dbui_build_structure(description) ──► Structure (regions + composition matches)
        │
        ▼
2. dbui_hydrate(structure, content)  ──► Spec (full tree with content + icons)
        │
        ▼
3. dbui_validate(spec)               ──► pass/fail per check, fix loop on fail
        │
        ▼
4. dbui_render_figma(spec)           ──► use_figma JS (or TSX, later)
```

The 4 primitives (`lookup_*` and `explain_component`) are used internally
by the orchestrators and callable directly when the LLM needs to inspect
or override a match.

### The Spec format

The contract between analysis and rendering. JSON tree.

```jsonc
{
  "shell": "BaseShell",                 // defaults to BaseShell
  "shellProps": { "activeNav": "Recents" },
  "content": [
    // dbui_build_structure ONLY populates this array.
    // Everything outside `content` is the shell, which is fixed.
    { "type": "PageHeader", "props": { "title": "Recents" } },
    { "type": "FilterPillBar", "props": { ... } },
    { "type": "ListView", "props": { "rows": [...] } }
  ]
}
```

Each `type` MUST be a known DBUI shell, composition, or component. Each
prop must match the component's documented schema. The Spec is medium-neutral
— same Spec produces visually identical output in Figma OR React because
component names + variant property names + slot semantics are 1:1.

## L4 — Processes

Scripts, rules, skills that drive workflows. Live in `.cursor/` and `scripts/`.

### Maintainer side (this repo)

```
db-design-system/
├── scripts/
│   ├── consumer-setup.sh               for end-user installs (later)
│   └── consumer-update.sh              for end-user updates (later)
├── .github/workflows/
│   └── drift-check.yml                 CI (later)
└── .husky/
    └── pre-commit                      regenerate L2 if L1 changed (later)
```

### Consumer side (after install)

```
their-project/
├── packages/
│   ├── dbui/                           copied from this repo
│   ├── dbui-shells/                    copied
│   └── dbui-mcp/                       copied (incl. pre-extracted L2 data)
├── .cursor/
│   ├── mcp.json                        registers dbui-mcp server
│   ├── rules/
│   │   └── dbui-scaffold-first.mdc     ALWAYS-applied rule (the enforcement)
│   └── skills/
│       └── dbui-build/SKILL.md         on-demand workflow guide
└── ... (their app code)
```

The setup script copies the three packages, writes the rule + skill, and
registers the MCP server. The update script overwrites — doesn't merge —
because L1 + L2 + tools + rule + skill are versioned as a single bundle.

## The four lifecycles

### 1. Setup (consumer runs once)

```
$ ./consumer-setup.sh

  1. cp packages/dbui          → their-project/packages/
  2. cp packages/dbui-shells   → their-project/packages/
  3. cp packages/dbui-mcp      → their-project/packages/   (incl. pre-built L2)
  4. cp .cursor/rules          → their-project/.cursor/
  5. cp .cursor/skills         → their-project/.cursor/
  6. write .cursor/mcp.json registration
  7. yarn install
```

### 2. Build a new screen / modify a screen (LLM, every UI task)

The rule fires automatically. The LLM follows the skill:

```
.cursor/rules/dbui-scaffold-first.mdc           ← triggers on UI tasks
        │
        ▼
.cursor/skills/dbui-build/SKILL.md              ← documents the steps
        │
        ▼ LLM calls in order:
   dbui_build_structure(description)            ← Stage 1
   dbui_hydrate(structure, content)             ← Stage 2
   dbui_validate(spec)                          ← Stage 3
   dbui_render_figma(spec)                      ← Output
        │
        ▼
   use_figma | TSX file write                   ← Real artifact
```

No L2 update during build — read-only.

### 3. Update (consumer pulls new components/shells)

```
$ ./consumer-update.sh

  1. git fetch upstream
  2. cp upstream/packages/dbui          → their-project/packages/
  3. cp upstream/packages/dbui-shells   → their-project/packages/
  4. cp upstream/packages/dbui-mcp      → their-project/packages/   (new L2 included)
  5. cp upstream/.cursor                → their-project/.cursor/    (latest rule + skill)
  6. yarn install
```

### 4. Drift-check (in this repo, CI + pre-commit)

```
yarn dbui:drift-check

  1. Re-run build-data.js to produce candidate L2
  2. Diff candidate vs. checked-in L2
  3. If diff exists → "Run yarn dbui:build-data and commit the result"
  4. Cross-check Figma file metadata vs. component-schemas.json
  5. Cross-check Figma layer names vs. figma-mapping.json
  6. Fail if Figma↔React names diverge
```

This is **the** mechanism that prevents collapse. Without it, hand-edits to
.md files or unsynced renames in Figma slowly poison the system. With it,
divergence is caught in seconds.

## What lives in `project/` (this folder) vs. `packages/`

| Location | Audience | Examples |
|---|---|---|
| `packages/` | Consumers (ships) | All L1 source, L2 generated data, L3 tools |
| `.cursor/` | Consumers (ships) | L4 rules + skills + mcp.json |
| `project/` | Maintainers only (gitignored) | This file, audit logs (`screenshot-eval.md`), in-flight reference docs that will be replaced by L2 generation (`figma-mapping.md`, `component-index.md`, `icon-index.md`), process notes (`change-impact-map.md`, `iteration-loops.md`) |

When the L2 auto-generation pipeline lands, the migrated reference docs in
`project/` become redundant — `packages/dbui-mcp/src/data/*.json` will be
the authoritative replacements, and `packages/dbui-mcp/scripts/build-data.js`
will produce optional human-readable `.md` views for review.

## Build order (when ready)

1. **Land L1 work** (current focus): refine Page Header, Tree, List, fix Platform Nav, add new shells/compositions in `packages/dbui-shells/src/`.
2. **Add new L3 tools** (in progress): `dbui_build_structure`, `dbui_hydrate`, `dbui_validate`, `dbui_explain_component`. Refactor existing 9 tools into the cleaner shape.
3. **Validate end-to-end**: rebuild a real product screen using the new pipeline. Compare to source.
4. **Tighten L2**: extend `build-data.js` to extract everything from L1 (ts-morph for schemas, Figma for mappings). Add `_manifest.json` + `drift-check.js`.
5. **Ship L4**: write the cursor rule, skill, setup/update scripts.
6. **Prove the loop holds**: a consumer copy + update cycle that survives a real component refactor in this repo.

Each phase makes the next cheaper. Don't extend until the foundation under it is clean.
